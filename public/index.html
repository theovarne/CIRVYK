01 / SYSTEM & INTERFACES

A market becomes a circuit.

CIRVYK turns a defined slice of token activity into bounded inputs, visible processing paths and replayable records. V1.1 restores the instrument around the V1 six-stage engine; it does not introduce a new consensus system or trading strategy.

The engine is a pure function of inputs, observation scope, epoch-aligned window, baseline and rules. Every page reads the same selected context. The Source workspace publishes the actual browser modules, configuration and documentation in an explicit public file set.

02 / SIX PROCESSING STAGES

One transaction, at most one Pulse.

A Pulse is a supported input admitted by the parser and the engine. A Trace describes one fixed processing window. A Snapshot is a PNG exported from a Trace. Multiple instructions in the same transaction do not multiply its Pulse count for the same target mint.

01 Sensor       normalize bounded inputs; preserve source and epoch timestamps
02 Resistor     verify eligibility; deduplicate; retain rejection reasons
03 Capacitor    accumulate accepted inputs inside [start, end)
04 Comparator   inspect the five preceding consecutive complete windows
05 Switch       select QUIET, FLOW or SURGE only for a final window
06 Memory       prepare the reproducible record for local persistence

Live inputs deduplicate by signature + mint; local fixtures deduplicate by input ID. Eligibility checks include time, source mode, parser verification, supported kind and scope. This is bounded filtering, not a complete anti-sybil or wash-trading detector.

The detailed SVG contains display structure as well as six interactive processing components. Passive traces, rails and framing are graphic topology. They do not claim independent online workers or additional processing stages.

03 / WINDOW & ROUTE RULES

Three paths. No hidden score.

QUIET

A reconciled, complete window contains zero valid inputs.

FLOW

The window contains valid inputs and does not meet the enhancement rule.

SURGE

At least 10 valid inputs and at least twice the mean of the preceding five complete consecutive windows.

Live observation uses 60-second epoch-aligned windows. Displayed times use US Eastern time (America/New_York), with automatic EDT/EST daylight-saving transitions. The start is inclusive and the end is exclusive. A baseline window must have the same scope and full rule configuration, be final, have complete coverage and complete parsing, and occupy its exact preceding position. A gap or conflicting count stops the consecutive baseline.

Engine stateConditionVisible conclusion
accumulatingThe current time is before window.endAccepted inputs may accumulate; path remains null
incompleteThe window ended but coverage, parsing or live scope is incompleteNo final path, including no QUIET conclusion
finalEnded window + complete coverage + complete parsing + configured scopeApply QUIET / FLOW / SURGE rules
Baseline unavailableFewer than five consecutive complete preceding windowsNo baseline average or growth ratio; non-empty final window is FLOW
Baseline average = 0All five qualifying baseline counts are zeroNo finite growth ratio; the count threshold still applies to route selection

Selecting a smaller time range filters the visible inputs and instruments. It does not recompute the whole-window route or invent a new baseline. The local Workbench can use 60, 120 or 300 seconds; this changes only its example Trace, not the live rule.

04 / TRACE FORMAT & MEMORY

Evidence travels with the trace.

The current record schema is circuit.trace.v1. These are actual fields returned by finalizeWindow(). Stored timestamps remain integer epoch milliseconds; the interface displays US Eastern time. Raw machine data and ISO strings retain their original instant; a missing derived value is null rather than a fabricated measurement.

Input fields are limited to id, signature, mint, slot, timestamp, kind, source, address, accounts, verified, scopeId. The live reader emits Activity or Transfer when supported evidence is available. Local fixtures have no transaction signatures.

Memory is local to this browser: at most 30 records and 3 MB. The newest windows are retained first; an updated record replaces the same fixed-window ID. JSON exports contain the inputs, baseline evidence and rule configuration. Import validates the data shape, reruns the actual engine, and compares every derived field before saving.

An imported file can declare live provenance, but that declaration is not a fresh chain verification. Imported historical records stay outside locally observed live counts and use historical labeling. A Snapshot is a downloadable PNG, not a public record link, a permanent shared memory or an on-chain write.

05 / OBSERVATION & COVERAGE

Observed does not mean everything.

The read-only Solana adapter queries explicitly configured accounts or pools, then examines finalized transactions for target-mint token balance changes or supported parsed SPL Token operations. A mint address alone does not index all token activity. Plain transfers are never relabeled as buys or sells, and an account-list match does not establish beneficial ownership.

Reader / coverage stateMeaningWhat the instrument does
unconfigured / invalid_configurationA required scope value is absent or invalidShow configuration scope; local examples and saved replay remain usable
ready / checkingConfiguration loaded / one shared request in progressRetain source labels, previous values and their timestamps
live + completeAccount scan, finalized timestamp boundary and transaction parsing reconciledFinalize only ended windows fully inside the proven interval
live + partialBounded pagination, pending parsing or only part of the range is provenExpose retained inputs and unresolved reasons; do not infer empty coverage
unavailable / error / rate_limitedA valid range cannot currently be establishedKeep the previous successful inputs and actual timestamps; allow another check
cursor_expiredThe bounded server cursor expired or changed scopeRestart once without that cursor; deduplicate the returned evidence

Only [reconciledFrom, reconciledUntil) is a proven range. Finalized slot and block time establish its upper boundary. Unresolved transactions constrain that boundary. Pagination limits and retention cutoffs cannot be presented as an exhaustive token history.

All seven pages share one reader. It checks approximately every 15 seconds while the page is open and visible; hidden-page polling pauses. Limits are four observed accounts, three pages of 50 signatures per account, 150 transactions per check, concurrency three and at most two retries. Cursor storage is bounded to 100 entries with a 30-minute lifetime. The interface keeps at most 4,000 retained input records by default.

A connected wallet supplies a public-address filter over observed account relationships. It requests no signature, approval, transaction or custody. Pasting a public address provides the same filtering purpose.

06 / OPERATING THE INSTRUMENT

One selection, across the panels.

  1. Choose a context. The shared context strip identifies local example, live scope or historical replay, with its actual window in US Eastern time. Load example opens an explicit fixture. Live scope exits replay and returns to the scoped reader.
  2. Inspect a component. Hover to preview, click to retain the selection. The circuit, relative activity display and inspector use the same selected stage. Drag or zoom the circuit; Reset view restores its framing.
  3. Select a time range. Each activity-grid cell has an explicit Eastern time interval and accepted count. Selecting a cell narrows the related input list and highlights the same waveform bins. Unknown coverage is not colored as a proven zero.
  4. Inspect an event. Open its input evidence and filter reason, then locate its processing path. Accepted final inputs pass through six stages; rejected inputs stop at the filter. An incomplete window can inspect accumulation but cannot replay a concluded route.
  5. Replay a saved Trace. Choose it in Memory. The selected context and related instruments switch to that record and retain the historical timestamp. Playback does not add live events.
  6. Recover the full view. Clear filters removes time, event and component filters. Live scope leaves replay; Home returns to the overview. Resetting the circuit view changes only framing, not data or counts.

Local Workbench procedure

Choose Single pulse, Short burst or Gradual flow. Set a 60-, 120- or 300-second example window and one to five input batches. The default batch contains respectively 1, 12 or 6 inputs; the maximum is 60 inputs. Each example carries five fixed preceding baseline windows with three accepted inputs each.

Parameter changes rebuild the example Trace, chassis readouts, waveform and output through the same engine. Execute local inputs advances the six stages; Pause retains the current step, Step inspects one stage, and Reset rewinds playback while retaining the selected parameters. Automatic or manual mode changes how the path advances. Speed choices of 0.5×, 1×, 2× and 4× affect playback timing only.

The Workbench is browser-local. Its restored chassis is a display model. No remote worker is registered, no CPU capacity is rented, no token is burned and no transaction is sent.

08 / QUESTIONS & REFERENCES

Read the mechanism, then inspect it.

Does SURGE mean buy or sell?
No. It is the result of a deterministic display rule over an observed count, not a forecast or valuation.
Why is an empty-looking circuit sometimes pending?
Missing evidence is different from a reconciled empty window. QUIET requires complete coverage, complete parsing and an ended window.
What works before a target is configured?
Local Workbench, full component inspection, the public Source workspace, saved-record import/export, replay and PNG Snapshot export. Live target observation needs a new mint and at least one explicit account or pool.
Does the system continue collecting when the page closes?
No. This version checks while open and visible. Memory persists only in this browser until records or browser storage are removed.
Can importing JSON prove an on-chain event?
No. The engine can verify internal consistency. Independent chain provenance requires a successful read through the configured observation scope.
